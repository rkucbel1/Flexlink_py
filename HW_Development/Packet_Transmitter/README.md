# Packet transmitter on the ADALM-Pluto

The Flexlink transmitter in the PL of the ADALM-Pluto (Zynq-7010, AD9363), so that one Pluto can
send packets at 40 Msps for as long as needed while the other Pluto (or the same one, by cable)
captures bursts for the Zedboard receiver (`../Packet_Detector`, bitstream 9.0, firmware build 16).
The Pluto's USB 2.0 cannot carry 40 Msps of samples (160 MB/s); the PL gets transport blocks and
the settings instead: 1.1 Mbit/s for the default settings, at most 26 Mbit/s.

The settings come from the files the simulator uses, `Tx/Parameters_Tx_payload.json` and
`Tx/ControlSignals/Parameters_Control_Field.json`. The PC sends their `Defined` sections in a
**control transaction** to a server on the Pluto's ARM (`FW/ptx_server`); the Pluto replies with
the `Calculated` sections and how many transport blocks make one packet, takes one packet of
blocks per credit, and reports every packet the PL has sent. It keeps transmitting with these
settings until the next control transaction. In the PL, every packet travels as a record: a
6-word parameter header (the `Defined` values) and the blocks; the PL derives the rest itself.

## Control transaction and block stream (PC <-> Pluto)

TCP to the Pluto's USB network address (192.168.2.1), port 5010. Every message: 16-byte header,
little endian (u32 magic `0x53585450` "PTXS", u16 type, u16 0, u32 seq, u32 length), then the payload.

| Type | Direction | Payload |
| --- | --- | --- |
| 1 PING / 2 PONG | PC -> / <- | - / JSON (server, protocol, build, stub) |
| 3 SET_PARAMS | PC -> | JSON `{"Tx": <Defined of Parameters_Tx_payload.json>, "ControlField": <Defined of Parameters_Control_Field.json>, "Gap": samples, "Gains": {...} (optional), "Radio": {"TxLo", "TxGain", "RfBandwidth"} (optional)}` |
| 4 PARAMS | <- | JSON: `ok`, `BlocksPerPacket` (AvailableDataBlocks), `TransportBlockSize`, `WordsPerBlock`, `PacketSamples`, `ControlMessage`, `Tx.Calculated`, `ControlField.Calculated` (the same keys and values as the JSON files' Calculated sections), `Header`; or `ok: false` and `error` |
| 5 BLOCKS | PC -> | one packet: u32 number of blocks, then the blocks, each TransportBlockSize bits from a new 64-bit word (bit j in word j / 64 at bit j % 64); seq = the PC's packet number |
| 6 READY | <- | JSON `credits` (and `depth` after PARAMS): packets the server can take |
| 7 SENT | <- | JSON per packet the PL has finished (`seq`, `sent`, PL `pl_packets`, `header_errors`, `underflows`); frees a credit |
| 8 STATUS / 9 | PC -> / <- | JSON: queued, on air, pushed, sent, credits, PL status word |
| 10 STOP | PC -> | ends the transmission, switches the Pluto back to its stock data path |
| 11 ERROR | <- | JSON `error` |

Two credits: one packet on air, one waiting in the PL's FIFO, so the transmission is continuous
while the PC keeps up; when it is late, the Pluto sends nothing until the next packet arrives. A new
SET_PARAMS waits until the queued packets are out, then applies to the next packets. The server
checks the control field's fixed settings (ControlMessageSize 54, Gen10, BCC K 7 [133, 171] 1/2
without tail biting, BPSK, 4 symbols, spacings 3, port 0, 40 Msps) and uses its C_init_ID1 (pilots)
and C_init_Dat (scrambler). The reference signals are generated in the PL from C_init_ID1 /
C_init_ID2 / the control field's C_init_ID1 and Mod (`ptx_check.py --only refs`: equal to all 32
`ReferenceSignals/Ref_P*_*.h5` files).

```bash
python ptx_client.py ping
python ptx_client.py send --packets 20 --run run1            # the JSON files, random blocks
python ptx_client.py send --forever --run run1               # cycle the packets until Ctrl-C
python ptx_client.py send --blocks <transport-block .h5>     # e.g. a file from Generate_File_Bitstream.py
python ptx_client.py status
python ptx_client.py stop
```

## Records in the PL (the server writes them into the TX DMA)

64-bit words through the Pluto's TX DMA, records one after the other. A record is a parameter
header and then `packets` × AvailableDataBlocks transport blocks; each block (TransportBlockSize
bits) starts in a new word, bit j in word j / 64 at bit j % 64. The server sends one packet per
record; `ptx_stream.py` writes the same records on the PC (`ptx_reference.param_header`,
`record_words`).

| Word | Bits | Field (JSON `Defined` key) |
| --- | --- | --- |
| 0 | [31:0] | magic `0x50584C46` ("FLXP") |
| 0 | [39:32] | header version (2) |
| 1 | [1:0] | Mod: 0 BPSK, 1 QPSK, 2 16QAM, 3 64QAM |
| 1 | [5:2] | RefSymbolSpacing (1, 3, 6, 12) |
| 1 | [10:6] | RefSignalSpacing (3, 6, 12, 24) |
| 1 | [17:11] | PacketLength (37, 49, 73, 97, 121) |
| 1 | [18] | Port |
| 1 | [19] | NumberOfAntennas - 1 |
| 1 | [20] | ClientFlag (0 Service, 1 Client) |
| 1 | [21], [22] | Use_Preamble, Use_ControlField |
| 1 | [24:23] | EncoderCodeRate: 0 1/2, 1 2/3, 2 3/4, 3 5/6 |
| 1 | [26:25] | EncoderBlockSize: 0 648, 1 1296, 2 1944 |
| 1 | [31:27] | Repetition (1, 3, 5, 7, 11, 15, 19, 23, 31) |
| 1 | [39:32] | C_init_Dat |
| 1 | [53:40] | Tx_Ref_Clk_Cnt (the simulator sends 0) |
| 1 | [55:54] | CRC: 0 Gen24 (the only one) |
| 2 | [30:0], [61:31] | C_init_ID1, C_init_ID2 (pilot Gold codes; any 31-bit value) |
| 3 | [15:0], [31:16], [47:32] | output gains preamble, control field, payload; 0 = the PL's own (13 dB backoff) |
| 3 | [63:48] | gap after each packet, in units of 16 samples |
| 4 | [31:0] | number of packets that follow (0: parameters only) |
| 4 | [63:32] | SampleRate in kHz (must be 40000) |
| 5 | [30:0], [61:31] | control field C_init_ID1, C_init_Dat (Parameters_Control_Field.json; 129, 130) |

The PL rejects a header with an invalid value (status: header errors) and looks for the next
magic word by word, as it does after garbage. From a valid header it computes NumberOfDataSigs,
AvailableDataBlocks (a 20-bit division), TransportBlockSize, ZeroPadding, the words of a packet,
the Gold start states of C_init_Dat, C_init_ID1 and C_init_ID2, the 54-bit control-field message
(NDB_A = AvailableDataBlocks) and its encoding, and the payload gain from a ROM per (Mod,
RefSymbolSpacing, RefSignalSpacing, PacketLength). A packet starts once all its words are in the
FIFO (4096 words), or the FIFO is full: always the case with a cyclic DMA buffer.

```bash
python ptx_stream.py --out stream.bin                       # JSON + 1 packet of random blocks
python ptx_stream.py --blocks ../../../Tx/Generate_RandomPacketOfData/Bitstream_TransportBlks_Tx.h5 --out stream.bin
python ptx_stream.py --decode stream.bin                    # headers and derived values
```

For the default JSON one packet is 91 words (728 bytes): 6 header words and 5 blocks of 17 words.

## The transmitter

Packet at 40 Msps, 12-bit I/Q (the DAC takes `{sample, 4'b0}`):

```
[ AGC 200 | Preamble A 10000 | Preamble B 2280 | control field 4 x 2280 | payload PacketLength x 2280 ] gap
```

```
 TX DMA ──> FIFO ──> bit buffer ──┬─> header ─> parameters ─> control-field encoder (CRC10, BCC, interleaver)
 (64 bit)   4096x64   128 bit      └─> ptx_enc: CRC24 ─> LDPC ─> interleaver ─> 2 code-word banks
                                                                                   │
   bit sources (copies, zero padding, Gold scrambler) ─> mapper (1 RE/clock, pilots from Gold(C_init_ID))
   ─> frequency buffer ─> feeder (level x AMP) ─> IFFT 2048 ─> output banks ─> player (preamble ROM,
   cyclic prefix, gap) ─> x gain, sat12 ─> async FIFO ─> DAC (l_clk, dac_valid)
```

* **Control-field encoder.** Message in the field order of `Parameters_Control_Field.json`, CRC10,
  6 tail zeros, BCC K = 7 (133, 171), the 140-bit interleaver; the bit source repeats it 15 times,
  pads 100 zeros and scrambles with Gold(control-field C_init_Dat, 130).
* **Payload encoder** (`ptx_enc.v`). Per block: TransportBlockSize bits from the stream (one per
  clock) and the CRC24 into 24 - m blocks of Z bits; λ_r ^= rot(block_c, P[r][c]) for the
  nonzero circulants of the message columns (one per clock, from a ROM of the 12 codes), p0 =
  rot(Σλ, hroll), then the dual-diagonal recursion; then the interleaver, one bit per clock, into
  one of two code-word banks. The same result as the simulator's G-matrix encoding. Worst case
  (64QAM, 2 copies) the encoder keeps up with 40 Msps: no output bubble in the tests.
* **Bit sources.** Copies of the code word (Repetition + 1), the next block, ..., ZeroPadding
  zeros, all scrambled with Gold(C_init_Dat), 1 to 6 bits per resource element. The Gold
  registers start from a state computed for any 31-bit c_init (`ptx_gold_start`, linear in c_init).
* **Mapper.** One resource element per clock into a frequency buffer of 841 level codes: Data REs
  take their bits (QAM_Mapper's Gray levels), Ref REs of the port take the next pilot bit
  (1, 0, 1, ... ^ Gold(C_init_ID1 or ID2; in the control field its own C_init_ID1), restarted every
  reference symbol) as a corner point, DC and the other port's Ref REs 0 - the rule of
  `Generate_Reference_Signal_Vectors.py`.
* **IFFT** (`ptx_ifft.v`): 2048-point radix-2² single-path delay feedback, 18-bit data, Q16
  twiddles, 1/2 after stages 3, 5, 7, 9, 11, saturation after every stage; SQNR against the float
  IFFT 72-75 dB.
* **Player and output stage.** Preamble from ROM (Preamble A: one 64-sample period; Preamble B
  body 2048 samples, the AGC burst is its first 200), symbols with cyclic prefix, gap. y =
  sat12((x × gain + 2^15) >> 16) per segment; the gains give preamble, control field and payload
  the same average power, as `Construct_Payload_Waveform.py` does, at 13 dB below full scale (the
  default control field peaks 12.3 dB above its rms). Use_Preamble 0 / Use_ControlField 0 leave
  the part out, as in the simulator.

### Control and status (no new AXI peripheral, no device-tree change)

`ptx_pluto.v` sits between the TX DMA and `tx_upack`, and between `tx_fir_interpolator` and
`axi_ad9361`, and uses the GPIO registers `axi_ad9361` already has (IIO device
`cf-ad9361-dds-core-lpc`: `iio_reg`, or pyadi `sdr._txdac.reg_write`):

| Register | Bits | |
| --- | --- | --- |
| `0x40BC` DAC GPIO out | 4 | 1: the DMA stream is Flexlink records, the DAC plays the core's samples; 0: stock Pluto (reset value). Bit 0 stays the FIR interpolator enable |
| `0x40B8` DAC GPIO in | [15:0] | packets sent |
| | [23:16] | header errors (saturating) |
| | [27:24] | DAC underflows inside a packet (saturating) |
| | 28, 29 | core busy, enabled |

Clocks: the core runs on `sys_cpu_clk` (100 MHz); DMA words arrive and samples leave in
`axi_ad9361/l_clk`, one sample per `dac_valid_i0`, through two 16-entry asynchronous FIFOs.

## Steps

### Step 0: Pluto to Pluto with stock firmware (no HDL)

The model's 12-bit samples in a cyclic TX buffer: the Pluto's DMA replays them from its RAM, so
nothing crosses USB after the first push. They are exactly the PL transmitter's samples.

```bash
pip install pyadi-iio
cd Flexlink_py/HW_Development/Packet_Transmitter/PC
python ptx_pluto.py tx --uri ip:192.168.2.1 --run run1 --packets 4         # PC 1, Pluto 1 (settings: the JSON)
python ptx_pluto.py rx --uri ip:192.168.2.1 --out cap1 --rx-gain 30          # PC 2, Pluto 2
python ptx_pluto.py check cap1.json --run run1.npz                           # bit-true model
python ptx_pluto.py check cap1.json --run run1.npz --board                   # and the Zedboard
cd ../../Packet_Detector/PC && python pd_hw_test.py ../../Packet_Transmitter/PC/cap1.json --input-stage 2
```

One Pluto, TX1 to RX1 by SMA cable with 30-40 dB of attenuation (never without):
`python ptx_pluto.py loopback --uri ip:192.168.2.1 --run run1 --out cap1`. The capture (2^20
samples = 26 ms, 4-5 packets with the default gap of 20000 samples) is a Zedboard input_stage 2
vector. Two Plutos are ±25 ppm apart: up to about 120 kHz CFO at 2.4 GHz.

### Step 1: the transmitter in the PL (this version: RTL done and simulated)

```bash
cd HW && vivado -mode batch -source synth_ptx.tcl && cd ..        # timing and resources first
git clone --recursive https://github.com/analogdevicesinc/plutosdr-fw.git ~/plutosdr-fw
chmod +x HW/patch_pluto_hdl.sh && HW/patch_pluto_hdl.sh ~/plutosdr-fw
cd ~/plutosdr-fw && export VIVADO_SETTINGS=<Vivado install>/settings64.sh && ADI_IGNORE_VERSION_CHECK=1 make
#   flash build/pluto.frm (copy it to the Pluto's mass-storage drive and eject), then the server:
cd FW && make -f ptx.mk pluto FW=~/plutosdr-fw && make -f ptx.mk deploy run PLUTO=192.168.2.1 && cd ..
cd PC
python ptx_client.py ping
python ptx_pluto.py loopback --mode pl --run run2 --out cap2       # control transaction + blocks
python ptx_pluto.py check cap2.json --run run2.npz --board
```

The server is built with the plutosdr-fw buildroot toolchain and sysroot (`FW/ptx.mk`: set
`CROSS` to the compiler prefix in `buildroot/output/host/bin` if it differs) and copied to the
Pluto's `/tmp`, which is RAM: copy it again after a power cycle, or add it to the firmware's root
file system. `--mode pl` sends SET_PARAMS (the settings as the two Defined sections, the radio
settings) and feeds the packets by credits until Ctrl-C. plutosdr-fw master builds with Vivado
2025.1; with 2025.2 the ADI scripts need `ADI_IGNORE_VERSION_CHECK=1`. The same captures as in
step 0 should decode the same way; with bit 4 at 0 the Pluto is stock.

### Step 2: files over the air

`ptx_client.py send --blocks` with the blocks of `Generate_File_Bitstream.py` (a file cut into
packets), the receive side as bursts on the second Pluto and the Zedboard, `Run_File_Transfer.py`
style bookkeeping of the blocks received.

## Notes

* The Zedboard receiver uses Ref_P0 with C_init_ID1 = 129 only (its pilot tables); the
  transmitter takes any port and any C_init_ID1 / ID2.
* The simulator scales the preamble and the control field to the measured payload power; the PL
  uses the expected power (difference below 0.02 dB).
